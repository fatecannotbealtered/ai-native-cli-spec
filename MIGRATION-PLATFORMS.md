# Migrating to three-platform packages

This is a draft for the next specification release; published tags remain unchanged. Pin the new tag only after it is released.

1. Inventory existing Windows, macOS and Linux packages and supported OS/architecture combinations. Keep those combinations while adding any missing OS. The template retains five native targets (Windows/amd64, macOS/amd64 and arm64, Linux/amd64 and arm64); three OSes with at least one architecture each is the product minimum, not permission to remove existing targets. Its Windows ARM64 npm alias uses the Windows amd64 binary under x64 emulation; claim it only after testing that path.
2. State minimum OS and CPU, external applications, services, licenses and system libraries. A standalone binary should carry its application runtime where practical; list the separate Node.js prerequisite of an npm wrapper. Identify any emulation explicitly and test it before claiming it.
3. Exercise the actual versioned archive on each supported combination: installation, startup and a representative key operation on an authorized real or controlled target. Record the archive digest, source version, environment and actual results. A host-limited application needs an operational remote client/host path and an explicit host OS, architecture and protocol.
4. Replace `scripts/smoke-product.js` with the real check and provide its runtime requirements. Its `prepare` returns the key-operation argv; the checker executes that actual installed binary, then `validate` checks its stdout. Each target writes one `smoke-<os>-<arch>.json` record, version 1.0. The release workflow directly runs `node scripts/check-platform-delivery.js check <archives-dir> <records-dir> <name> <version> --expected-source-sha <40-digit-commit>`, which verifies the records, actual archive and executable digests and executable OS/architecture; it requires at least one passed target per OS and a matching passed record for every archive. The checker uses `tar` and, for ZIP on Linux/macOS, `unzip`; these are build/check tools, not direct-binary runtime requirements. Run `smoke` on each native target to produce the records. A failed or unrun result remains failed or unrun. Preserve authorization, security tests, audits and existing signature verification.
5. A 2.0.1 tool may move R06 from a hard release gate to a separately reported full-coverage check: keep the real failure and missing-command list. A full multi-model eval is not a universal platform-support gate; only claim the maturity and evaluation supported by actual evidence. Continue fixing and testing remaining commands, recovery cases and additional architectures.

No package, check or operating-system test is implied by adopting this text.
